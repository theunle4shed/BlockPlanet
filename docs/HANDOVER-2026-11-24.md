# Handover, 2026-11-24

For whoever picks up BlockPlanet next (a person or a new Claude session). It covers how the project works, where everything is, what was done in the session of 2026-11-01 to 2026-11-24, and what comes next.

## The project in one paragraph

BlockPlanet is a PC version of Tetrisphere (N64), carried on from djultra64's **Blocksphere**: the game's code recompiled with N64Recomp, drawn by RT64, with BlockPlanet's own menus, HUD, sphere drawing, power-up models and many fixes on top. Nothing derived from the ROM is in Git: the player builds from their own copy. Credit Blocksphere and djultra64 wherever the project is described.

## Building and testing on Linux (the test machine)

- **Build:** `cd .local/m1/build-gcc && ninja`, then `ctest` (83 tests).
- **After changing `config/recomp/tetrisphere.us.rev0.toml`** (the hooks), regenerate the game code first:
  ```
  rm -rf .local/m1/linux-generated .local/m1/linux-generated-manifest.json
  python3 -m tools.recomp.generate generate --rom .local/m0/tetrisphere-us.z64 --output .local/m1/linux-generated \
    --manifest .local/m1/linux-generated-manifest.json --recompiler .local/m1/toolchain/n64recomp-build/N64Recomp
  cd .local/m1/build-gcc && cmake . && ninja
  ```
- **Hooks:** a function can have one entry hook (combine conditions in one text); `before_vram = 0x...` hooks go inside a function.
- **The harness:** `tools/qa/harness/` (README there). This session's versions are in `tools/qa/harness/session-2026-11/`:
  - `nav98.sh` / `run98.sh` drive the game in a virtual display;
  - `zoom.py` makes frame sheets from a recording;
  - `measure.sh` counts bricks removed per power-up on a fixed sphere;
  - `audit_rescue_endings.sh` records each Rescue episode's ending.

  They expect `BP_HARNESS` (default `/tmp/bp-harness`) to hold the scripts and their output folders. Copy the folder there to use them. Space harness pad presses out, or it aborts ("multiple unacknowledged commands").
- **Known harness quirks:**
  - **Exit code 139:** the software graphics driver's crash. Run again.
  - **Fps 0 / launch timed out:** a stall. Run again.
  - **One game at a time:** two games at once share display `:98` and kill each other.
- **Low frame rate:** the test machine runs at about 15 fps, so smoothness is judged from the owner's recordings.

## What the session did (headlines; details in CHANGES-SINCE-BLOCKSPHERE.md)

- **Power-ups:**
  - **Now:** the original six as in the game (the Firecracker first, each one earned while holding one moves up the ladder), with BlockPlanet's icons and 3D models for each, a flickering flame on the Bomb, and **losing a life keeps the held power-up** (the owner's one change from the original).
  - **Kept as research** behind `BLOCKPLANET_POWERUP_LEVELS=1`:
    - levels 1 to 3;
    - the Missile Barrage (launcher, three missiles, one wide blast);
    - Dynamite's bigger holes and outer ring;
    - a set order of power-ups per stage by the sphere's depth.

    Measurements of each are in docs/research/blockplanet-score-and-magic.md.
- **Crash fix:** the frame's display list overflowed the game's buffer when BlockPlanet added drawing, overwriting the other frame's list. Lists now get 256 KB buffers above 4 MB (`blockplanet_frame_list_buffer`). RT64 skips and logs a matrix outside memory as a safety net. Windows crash reports name functions.
- **Endings:** Episodes 5 and 8 fixed (above).
- **HUD:** green hearts; lost ones show as an outline.
- **Crafted bricks:** crystals turn white when about to break. Textures made in earlier sessions load at start-up.
- **Research findings worth knowing:**
  - **How power-ups are chosen:** the original uses a ladder (+1 per earn).
  - **The game's limits on blasts:**
    - one shared blast centre and timer;
    - a per-cell table each blast resets;
    - a list of bricks waiting to break, counted in one byte, so at most 255;
    - room for about 8 explosions at once.
  - **Episodes 5 and 8** play the game's ending (curtain call and credits), as Episode 10 does.
