# Menu layer (BlockPlanet)

BlockPlanet's new menus are built with [RmlUi](https://github.com/mikke89/RmlUi), an MIT-licensed library that lays out documents written in an HTML- and CSS-like language (RML and RCSS). BlockPlanet draws them over the game itself, through RT64.

RecompFrontend, the menu library other N64: Recompiled projects use, was not used: it has no licence, so BlockPlanet may not ship its code. Blocksphere kept it as a reference only. BlockPlanet's renderer was written independently.

## How it works

| Part | File | Role |
| --- | --- | --- |
| Renderer | `src/ui/ui_renderer.cpp` | Implements RmlUi's render interface on RT64's graphics layer (plume): geometry in host-visible buffers, textures uploaded through a staging buffer, scissor regions and transforms. Fonts and images become textures; PNG images are decoded with stb_image (compiled by RT64). |
| Shaders | `src/ui/shaders/UiVS.hlsl`, `UiPS.hlsl` | Pixels to clip space with RmlUi's transform; premultiplied-alpha colour times the texture. Compiled with RT64's DXC to SPIR-V (and DXIL on Windows). |
| System | `src/ui/ui_system.cpp` | Registers RT64's render hooks before RT64 starts, starts RmlUi when a menu first opens, applies queued requests and input on the presentation thread, and updates and draws the context while menus are open. |
| Navigator | `src/ui/ui_navigator.cpp` | Screens and focus (below). Uses RmlUi only, so it is unit-tested without RT64 (`tests/ui_navigator_test.cpp`). |
| Menu input | `src/platform/menu_input.cpp` | Turns SDL keyboard and controller events into menu actions while menus are open. |
| Assets | `assets/ui/` | Screens (`screens/*.rml`), the shared style sheet (`menu.rcss`) and fonts, copied beside the game into `ui/` at build time and included in the release package (`BLOCKPLANET_UI_ASSETS` overrides the folder). |

- **Threading:** RT64 calls the draw hook on its presentation thread, after drawing the game and before presenting. All RmlUi work happens there. Other threads use `request_open`, `request_close` and `queue_action`, which are applied at the next frame, and read the player's choices with `take_command`.
- **Scaling:** documents are designed for a 1080-pixel-high screen using `dp` units; the density-independent pixel ratio is the window height divided by 1080, so a layout looks the same at any resolution.
- **Resources:** released geometry and textures are kept for four frames before being freed, since RT64 may still be drawing earlier frames.
- **Fonts:** Lato (SIL Open Font License), family name `LatoLatin`. Others can be added to `assets/ui/fonts`.
- **Dependencies:** RmlUi 6.2 and FreeType 2.13.3 are pinned in `config/dependencies-m1.json` and built statically from `.local/deps` (`cmake/BlockPlanetUI.cmake`).

## Screens and input

A screen is an RML document in `ui/screens/<name>.rml` that links `../menu.rcss`. Elements with the class `item` take focus in document order (items with the class `disabled` are skipped); the focused one gets the class `focused`. Up and Down move the focus, wrapping around. Confirm runs the focused item's `data-action`:

| Action | Effect |
| --- | --- |
| `open:NAME` | Shows screen NAME on top. The screen being left keeps its focus for when the player comes back. |
| `back` | Goes back one screen; from the first screen it closes the menus. Also what the Back input does. |
| `close` | Closes the menus. |
| `command:NAME` | Reports NAME to the game, which logs it as `ui_command`. `exit` closes the game; `profiles` and the `profile…` commands run the profile screens; `story`, `time_trial`, `lines`, `puzzle`, `versus` (and `hide_and_seek`) start a mode (below); the others are not connected yet. |

**Setting rows** have the classes `item value` (add `slider` for a row that stops at its ends and shows a bar: a child `.bar` holding `.fill`), `data-setting="NAME"` and `data-options="value:Label,value:Label"`, and show the current value's label in a child with the class `value`. Left and Right (and Confirm) cycle the value and report `setting:NAME=VALUE`; the game applies and saves it through the same path as the PC settings menu, then sends the saved value back, so the row always shows what was saved. Current values come from `set_setting`.

**Grids:** items directly inside an element with `data-columns="N"` form a grid, filled row by row; an item with `data-span="K"` takes K columns. Left and Right move along a row, wrapping at its ends. Up and Down go to the item covering the same column in the next row, remembering the column across wide items; at the top and bottom they wrap if the grid has `data-wrap`, and otherwise leave the grid. Give grid items widths as shares of the row (see `.keys` in `menu.rcss`) so each row holds exactly N.

**Controller or keyboard:** while a controller is used, every screen's body has the class `pad`; `.for-pad` parts show only then and `.for-keys` parts only otherwise. The first controller press or keyboard key switches.

**Section headings:** an element with the class `section` labels the rows below it; it takes no focus.

**Text fields:** an element with `data-text="NAME"` shows the text given to `set_text` (as plain text).

**Lists the game fills in:** an element with `data-list="NAME"` gets the items given to `set_list` when its screen opens (label, note, action; disabled entries are skipped). An item marked `focus` takes the focus when the screen opens.

Screens get the class `entering` when opened and `returning` when shown again after going back, which `menu.rcss` uses for a quick slide (0.18 s).

Input while menus are open:

| | Keyboard | Controller |
| --- | --- | --- |
| Move | Arrow keys | D-pad, left stick |
| Confirm | Enter, Space | The profile's confirm button (A by default), Start |
| Back | Escape, Backspace | The profile's cancel button (B by default), Back/Select |

While menus are open the game receives no input, and after they close it stays blocked until every button is released, so the closing press does not reach the game. For now F1 opens and closes the menus, and `BLOCKPLANET_UI_TEST=1` opens them at start; the game keeps running behind them.

## Starting modes

**Story, Training, Puzzle, Lines, Hide & Seek and Versus start directly** (2026-11-09; the others 2026-11-10): BlockPlanet does what the original menus do for them on the game's thread and hands over to play at once, so the player page, the grid's fly-in and fly-out, the menu music change and the transition sounds never run (`src/graphics/direct_start_hooks.cpp`; research in [blockplanet-game-state.md](research/blockplanet-game-state.md#starting-modes-directly-2026-11-09)). It works from the game's main menu (behind BlockPlanet's); from anywhere else it waits up to two seconds, then falls back to `ModeLauncher`. `BLOCKPLANET_LAUNCH=menus` always uses `ModeLauncher`. The log shows `mode_launch` with `"route":"direct"` and a `direct_start` event. The original Time Trial (not offered in the menus) still uses `ModeLauncher`.

`ModeLauncher` (`src/platform/mode_launcher.cpp`) starts the game's modes by driving the original menus, so the game sets each mode up exactly as when a player chooses it. From the title, the main menu or the player page it puts the original menu's cursor on the right item and presses A (on port 1, through `get_input`), step by step:

1. Main menu row (`0x800E121C`) to SINGLE, press, until the player page opens (`0x800E1222` ≥ 0).
2. Player page row to START, press, until its mode list is active (`0x800E1224` ≥ 0).
3. Mode list row to the mode's row, press, until play begins (`0x800E121C` = −1).

Mode list rows (the player page's table at `0x800EDAE4`): 0 Rescue (mode 1), 1 Hide & Seek (5), 2 Puzzle (4), 3 Time Trial (2), 4 VS CPU (6), 5 Lines (mode 9). The original menu lists only rows 0 to 4 until Lines is unlocked; the launcher starts Lines directly, which is how BlockPlanet makes it available from the start.

Requests are refused during play and inside other original pages such as Options, and give up after 15 seconds. The log shows `mode_launch` with `started`, `playing`, `refused` or `timed_out`. Checked from the title in the Linux test setup: Story (Rescue 1:1), Time Trial, Lines (its rules screen), Puzzle and Versus (VS CPU) all start.

## Menu grid

The owner's design (2026-11-09; roadmap: One grid background for the menus). BlockPlanet draws the game's tiled grid as one background of its own (`src/ui/ui_grid.cpp`, `assets/ui/grid.rml`), always behind the menu screens (its document is pushed to the back every frame) and above the game's picture and HUD.

- **Colour per screen:** `data-grid="blue"` (or green, red, purple, gold, grey, cyan, teal, peach; `grid_colour` in `ui_grid.cpp`) on a screen's body, or a cycle (`data-grid="pause"`: purple `#26152f`, deep blue `#0f1b2c`, grey-blue `#262b30`, teal `#0f2131` and green-grey `#242c25`, fading smoothly from each to the next over 5 seconds; sampled from the original pause's background, its average colour once a second for 40 seconds, which loops in about 22 to 25 seconds; `grid_cycle`). The owner's "peachy red" was not in the averages: probably the lit tiles' highlights, to tint warmer if wanted. Coming from another colour, the tiles flip into the cycle; within it they fade together, without flipping. The grid shows while the first open screen has one, in the colour of the highest open screen that has one. Screens over the grid get the class `on-grid` (their dimming background is dropped, `menu.rcss`). The pause menu has the cycle, so the grid hides the board there too.
- **Shades:** tile colours sampled from the original (blue `#0d151f`, highlights `#141f2d`, shadows `#080d14`; red `#2b0510`); green is a matching dark teal-green `#0b1d18`. The far background behind the tiles is the tile colour at 45 %.
- **Shape (the owner's notes, 2026-11-09):** 8 × 8 tiles, patches of one sphere between lines of equal angle across and down, 62° either side of the middle (not quite a half sphere), so each row's top and bottom edges and each column's sides follow one smooth curve across the grid, with the gaps between tiles as its lines. Rows and columns are treated alike (each line a great circle: the rows' through the sphere's left and right sides, the columns' through its top and bottom), so rows bow as much as columns: a symmetric bulge, like the original's tile sphere seen head on (latitude and longitude, tried first, left the middle rows almost straight). The sphere stays round and is sized by the screen's shorter side: there the middle of the outermost tiles is at the screen's edge, so they are cut in half (the owner's note, 2026-11-09); along the longer side the far background shows beyond the outermost tiles. Each tile is an `img` element drawn from a 128-pixel square at the top left, carried onto its patch by one `matrix3d` per tile: `grid_tile_corners` works out where the patch's four corners are seen (each corner's lift on the water, the tile's flip and flight, then perspective from the screen's middle), and `grid_quad_matrix` maps the square onto them in perspective. A quad folded by perspective (its depth crossing zero inside it, as happens to rim tiles lifted unevenly by the water or turning) gets no matrix, since a GPU would stretch it across the screen: the tile is drawn flat instead, or hidden. The capture tool clips like a GPU, so such faults show in captures. Shaded by a light from the upper left. Constants at the top of `ui_grid.cpp`.
- **Water (the idle motion):** the owner's description of the original: the tiles bob like floats on gently rippling water. Each corner of every tile follows a water surface (`grid_water`): a wave travelling from the top left (each tile rising and sinking once every 1.5 s, each next tile along the diagonal 0.2 s later) and a weaker ripple crossing it at an angle, so each tile rises, sinks and tilts on its own. It is part of each tile's matrix, so it carries on through flips and flights. The owner finds the original's tiles "more independent": `independence` blends the shared water with each tile bobbing on its own (its own phase, a speed up to `speed_variation` faster or slower, and its own tilt, `tilt` against its rise). Defaults measured from the original with the tool (2026-11-09, 390 frames at 30 fps): period 1.43 s, one clock for every tile (the original's brightness period spread is 0.002, so no speed variation, no cross ripple of another period, and the tilt on the same clock; ours measures 1.433 s with no spread since), about 60 % independent with neighbours barely alike, about 0.35 s per tile along the wave, and tiles tilting more than they rise (tilt 100 %). `tools/qa/grid_motion.py` measures a recording of the original's grid (period, how much periods differ, the wave's direction and per-tile delay, how much of the motion is not one travelling wave, neighbours' correlation, tilt against rise) and suggests test-screen settings; `--selftest` checks it on frames of a known motion. Panel-free recordings of both (the parent session, 2026-11-09, centre of the grid) agree on the single clock, tilt against rise (2.02 against 1.87) and independence (0.63 against 0.65 by position); the original's brightness changes per tile with little travelling (delay 0.06 s against our 0.65 s). Lighting each tile by its tilt (Tilt lighting) was tried for that and measured further from the original, so it is off by default; `UI_CAPTURE_SEQUENCE=SECONDS` makes the capture tool write a frame sequence of our grid alone (panels hidden, 640 × 480, 30 a second; `UI_CAPTURE_SET=name=value,...` sets test-screen values first) to measure ours the same way. Breathing of the whole sphere (measured from the original's: 1.5 s, about 2.4 % peak to peak) was tried and removed (the owner's choice). The original also has faint dark round "coin" shapes (the robot medallions) drifting around the sphere's edges; not added yet.
- **Changes:** the same colour stays still. A new colour fades the far background and flips each tile half a turn about its upright axis, starting one after another from the top left (`grid_flip_seconds`, `grid_ripple_seconds`); past halfway a tile shows the new colour. Nothing queues and input never waits: each tile always heads for the newest colour. A tile not yet past edge-on carries on to it; one already showing an older colour finishes its turn and flips again when the newest ripple reaches it. Tested with rapid back-and-forth presses (every tile ends on the newest colour, none jumps between frames).
- **Cost:** about 0.4 to 0.7 ms of the presentation thread per frame at 1920 × 1080 (release build, Linux test machine, measured with RmlUi and a renderer that draws nothing), mostly the wave's 64 transforms. Properties are set only when they change, since RmlUi rebuilds an element's shape (and the renderer makes new GPU buffers) whenever one is set, even to the same value; the first version set the far background every frame, the likely cause of the credits' stutter on this branch. A tile's colour changes only a few times per flip (its edge-on darkening is in steps).
- **Texture:** the game's grey marble from the player's ROM (main archive entry `0x000`, 160 × 120, 8-bit; `grid_texture.cpp` unpacks pass J), read once at run time and kept only in memory. Four square parts of it, each with a bevel, make the tiles' texture, tinted by `image-color`. Without the ROM's texture a procedural marble is used.
- **Flying in and out (step 2, the owner's notes 2026-11-09):** whenever a screen with a grid opens and the grid is not up (after the title, over the game's pause), the tiles fly in from past the viewer to their places, the outermost first and the middle last, while the far background fades in over whatever is behind (whole by half way); they start near the viewer rather than past them, so they show from the first frames. Whenever the menus close, they fly out mostly outwards past the screen's edges and a little towards the viewer (`fly_out` 2.2 sphere radii, `fly_toward` 35 % of the viewer's distance; the owner found them coming too much at the viewer), each turning to face the viewer as it sets off (kept facing outwards, rim tiles were seen nearly edge on as long thin wedges), the middle first, so the grid opens from the middle; the far background fades in step with them both ways (between 0.75 and 0.4 of the way in place, where the tiles go), so they reveal the game itself (straight at the viewer, the tiles filled the screen in their own colour near the end, which read as a flat dark screen; each tile now covers at most a tenth of the screen and is dropped once near the viewer) (`grid_fly_seconds`, `grid_fly_spread`; about 0.7 seconds in all). Launching a mode from the menus, the grid is the loading screen (the owner's design, 2026-11-09): it stays in the colour it had, the water moving, with the mode's name over it (the loading cover's text, outlined, without its dark background) while the game's menus are pressed through and the stage loads, until play has run 1.2 s with the game's own fade (`0x800E1202`) clear (`BLOCKPLANET_GRID_LOAD_MS`; Story's stage still fades in for about 1 s after that value reads 0, recorded 2026-11-09; 4 s of play at the latest, 20 s in all at most); then the tiles fly out to reveal the stage already showing, and the HUD appears once they have gone. Effects stay muted meanwhile, as under the cover. The same for every launch (Story, Training, Puzzle, Lines, Hide & Seek, Versus, a restart from the pause in the pause's colours). Without a grid up (a pending Continue), the dark loading cover is used as before; a grid that leaves while a load is still wanted flies into it (the far background kept, the cover rising as the tiles pass, `cover_allowance`). A change of mind part way carries on from where the tiles are, and the water and flips carry on throughout. The game shows the grid over its own pause animations, in the pause's colours (`set_grid_override`, `linux_main.cpp`): from the Start press that pauses (so the game's own fade and big pause tiles are never seen), while paused, after Resume until the pause row `0x800E1228` clears and a moment more (`BLOCKPLANET_GRID_RESUME_MS`, 150 ms; 450 ms when the exit runs its full length, about 2 s after Resume). Measured on the test machine: the game's screen fade (`0x800E1202`, 255 while paused) is clear within about 0.4 s, then the game flies its own pause tiles out over the play field for about 1.3 s before the row clears. The owner finds Resume slow; to shorten it the game's pause tiles must not be drawn after Resume. Skipping the pause background helper (`set_pause_exit_hidden`, with `BLOCKPLANET_GRID_RESUME=fade`, which then leaves once the fade is clear) did not hide them (recorded 2026-11-10): they are drawn elsewhere, still to find. So BlockPlanet ends the exit early instead (since 2026-11-10; `BLOCKPLANET_RESUME_SKIP=0` turns it off): once the exit has faded in, `0x800DFF08` = 0 and the row -1, as at its natural end, the game's pause request flag `0x8013FAD0` cleared, since while it is set and the row is -1 the game's main loop (`func_80070118`) starts a pause again, and BlockPlanet's pause bridge stops driving the row, which had also written it back; the grid then leaves 150 ms later, so from pressing Resume to seeing play takes about 1.3 to 1.4 s (about 2.9 s before; read from captured frames, Story 1:1, two cycles, 2026-11-10). After Quit to menu the grid stays until BlockPlanet's menus open again, when it ripples to their colour. A Start press that does not pause within 1.2 seconds lets the grid fly out again.
- **Research log:** `BLOCKPLANET_GRID_LOG=1` writes a `grid_frame` line every frame while the grid is drawn (and the frame it goes): the time, the colour asked for (the game's `pause` included), whether it is drawn, flying out or flying into the loading cover, how much is in place and the far background's strength. It also writes a `ui_frame` line each frame while the grid is up and for 1.5 seconds after it goes: which of BlockPlanet's layers are shown (menus, HUD, loading cover, build label, grid) and every visible document with its opacity.
- **Grid test screen (temporary, the owner's request):** Options > Grid test (`grid_lab.rml`) shows the grid behind a narrow panel with live sliders: the water's wave period, each next tile's delay, the cross ripple, the wave's height, independence and speed variation (the owner asked for the water's settings only); how far tiles fly outwards and towards the viewer; what to show (tiles and background, tiles only, background only); fly time, spread and distance; the colour (every named colour and the pause cycle); and Fly in and Fly out buttons. Flown out there, a black backdrop stays behind the grid (`set_backdrop`), so the game's own menus are not revealed and the animation can be judged on its own. Changes apply at once and are not saved; each is written to the log as a `grid_tuning` line with every value, for reporting. The settings live in `GridTuning` (`grid_tuning()`), whose defaults are the values chosen so far. The HUD is not shown while the grid is up or flying.
- **Tuning:** the defaults are accepted for now (the owner, 2026-11-09); final tuning is deferred until much later, on the grid test screen. Known differences from the original: the grid is smaller than the original's background, which fills a 4:3 screen's width (ours is sized by the shorter side, the owner's choice), and its light sweeps across the grid as a wave (tile to tile about 0.65 s) where the original's changes per tile almost at once (about 0.06 s); lighting each tile by its tilt was tried and measured further away.
- **Not yet:** red tiles flying in behind BlockPlanet's game over panel once the GAME OVER animation has shown (waits for the research on holding the game over screen); a different idle motion per section (the owner's idea); the title screen on the new grid. The title's ring, logo and characters are drawn by the game, under BlockPlanet's layer, so the grid would hide them: putting the title on the grid needs the grid drawn before the game's picture (in the renderer) with the game's own grid switched off, or the title's parts rebuilt by BlockPlanet.

## The box art on the grid

The owner's design (2026-11-10): the title's box art (BlockPlanet's held title scene: the 3D letters, the ring, Turbine, Wheels, the Bombs and the core light) stands on BlockPlanet's menu grid, so the grid is already up when the menus open. The game draws the box art, and BlockPlanet's grid is normally drawn over the game's picture, so it is put under it instead:

- **The game's side** (`src/graphics/box_art_hooks.cpp`): while the title shows (`0x800E1648` = 1, `0x800E1646` = 0), the title routine's backdrop (the grid sphere, its own scene at `0x800E1674`, drawn first) is skipped and a fill of the whole frame drawn instead, in a blue near the grid's tiles (`0x0B121A`). RT64 keeps the fill's alpha (1, the 16-bit colour's low bit), and everything the box art draws over it writes alpha 0, its core light's glow included (it lies inside the ring's solid interior). So the game's picture carries the box art's outline as its alpha. The edge is hard: pixels at the box art's edges are already blended with the fill, which is why the fill is close to the tiles.
- **The renderer** (`include/tetrisphere/under_layer.h`, `tools/build/patch_rt64_probe.py`): while `under_layer::wanted()` is set, RT64's present first calls BlockPlanet's under layer, then draws the game's picture with a patched copy of its picture shader (`VideoInterfaceCoverPS`, written by the patch script from RT64's own and compiled with BlockPlanet's shaders, for Vulkan and, on Windows, D3D12) that writes the picture's coverage (1 − its alpha) as alpha, blended over what is there. Otherwise nothing changes.
- **The menus' side** (`src/ui/ui_system.cpp`): the grid has an RmlUi context of its own (`grid`). Each frame is prepared once (requests, grid, HUD, update), then the grid is drawn in the under layer when that runs, or else first in the normal layer, behind the menus as before. The title's notice (part of the HUD) still shows while the box art is over the grid; the rest of the HUD does not.
- While the box art shows, the main loop asks for the blue grid (`set_grid_override`), so it flies in as for the menus. `BLOCKPLANET_BOX_ART=0` keeps the game's own backdrop.
- Checked at 16:9, 4:3 and 21:9: the box art's edges and glow over the grid, the notice beneath; the menus and the pause over the grid unchanged.
- **From the intro** (`box_art_hooks.cpp`): when the intro's scene (`0x800E1670`) reaches frame 1185 (Wheels has flown past the camera and off; the intro's own end is near 1230), that frame's intro scene is not drawn, and at the start of the next frame, before the intro runs (`box_art_frame`; changing the intro's state from inside its own frame, as the first version did, is not safe), BlockPlanet ends the intro as the intro does itself at its end (`0x800685BC`: `0x800E1208` and `0x800E120C` cleared, `0x800E1648` = 1, the scene memory `0x800F22C0` rewound to `0x801028D0`), and that frame's intro scene is not drawn (its memory becomes the title's). The title then plays its letters' fly-in as in the original (in time with its song, 308, which has the hit for their explosion; the owner's choice after seeing them start formed) and holds them once formed; the ring, the robots and the light come in after them, where the painted picture would have appeared. `BLOCKPLANET_BOX_ART_INSTANT=1` starts with the letters already formed: the freeze hook (`title_hooks.cpp`) then steps the letters' scene to the held frame with `func_8002F55C` at once (setting the frame alone leaves the letters unformed). The box art fades in over the grid as it flies in: the under layer's fade (`under_layer::picture_fade`, eased over 1 s from each start of the layer) reaches the blended picture shader folded into its gamma constant, through a patched copy of RT64's `rt64_vi_renderer.cpp` (gamma + 4 × round((1 − fade) × 1000); RT64's gamma is 1 or less than 4). `BLOCKPLANET_BOX_ART_CUT=0` plays the intro to its end.
- **The flow** (`box_art_frame` in `src/graphics/direct_start_hooks.cpp`, once a frame in the game's main loop before the intro or title runs; `blockplanet_box_art_update` there also sets whether the box art shows, so the under layer follows the title exactly, as the menus' first frames draw no scene):
  - **Skip:** A or Start during the logo or the intro (once the save has been read) ends the intro at once, as the hand-over does, so the box art fades in with the grid flying in.
  - **Hold:** on the box art the title's own timeout (`0x800E1208` reaching 901 frames, 15 s) is held off at 880.
  - **Press:** A or Start leaves the title as it does on a press (`0x80069500`: the music players stopped, `0x800E16B4` = 1, player 1's controller, the scene memory, `0x800E1646` = 1 and the exit count), done by BlockPlanet because the title reads its buttons (`0x800DFD98`) after they are polled again that frame, and it waits 4 s before taking a press; the game's Training jump for a brand-new save (`0x800DFE8C`) is cleared, so the menus come up. The main loop keeps the blue grid asked for half a second after the box art goes, and the menus open over it without it moving.
  - **Attract:** after 15 s (`BLOCKPLANET_ATTRACT_SECONDS`), the title is let leave by its own timeout, and once the game is in its main menu (behind BlockPlanet's grid, which stays asked for, and with BlockPlanet's menus kept closed), its idle timer is run out: the time of its last input (`0x800E1214`) is set 32000 frames back, so the main menu's own check (`0x8004FB3C`: `0x800E1208` − `0x800E1214` against the threshold at `0x800DFD48`) starts the demo as after sitting idle: mode 10 (or 3 every sixth time), `0x8015D980` = 1, then its grid flies out. When play starts (`0x800E121C` = −1, mode 10 or 3), the grid is no longer asked for and flies out over the demo. When the demo ends the game returns to its title (`0x800E1646` = 0), which BlockPlanet restarts from its start (scene memory, phase `0x800E1650` = 0, counters): the title builds its scenes only from phase 0, and the held letters never let it get there by itself. (`0x800DF728` and `0x800E11F8`, the top loop's other attract path, is not the demos: set from the title, nothing plays.)
  - **Back:** B on the box art plays the launch animation again (the intro restart). Back from "Who is playing?" (`back_to_title`) asks the game's thread for a title restart instead of an intro restart, and the grid stays asked for until the box art is back (3 s at most).
  - BlockPlanet's menus stay closed while the game is on its intro or title (`0x800E1646` = 0) with the box art on, and through the demo.
- Checked in the Linux test setup (16:9, guest): the intro into the box art; 15 s idle, the demo (tiles out), its end ("Nice job") and the box art again, then the next demo; Start during the intro to the box art; A on the box art to the main menu over the same grid; B on the box art to the launch animation and back to the box art. Not yet checked: Back from "Who is playing?" (needs more than one profile), Windows (D3D12). One test run of about fifteen ended with the game crashing near the hand-over from the intro (not seen again in repeats); to look into.

**Testing without the game:** `cmake -S tests/ui -B build-ui && cmake --build build-ui && ctest --test-dir build-ui` runs the menu tests (RmlUi and FreeType in `.local/deps`). `cmake --build build-ui --target ui_capture`, then `build-ui/ui_capture assets/ui OUT [rom.z64]` writes captures of the main menu, Solo, Story, Options and the pause menu over the grid (the wave frozen at one moment), and three frames of a colour change, at 4:3, 16:9, 21:9 and portrait, drawn by RmlUi in software (pictures such as controller art are left out). ## In-game HUD

BlockPlanet's HUD (design in [HUD_DESIGN.md](HUD_DESIGN.md)) is a separate RmlUi document, `assets/ui/hud.rml` with `hud.rcss`, in the same context as the menus. The game thread fills `blockplanet::ui::HudView` each frame (`update_hud` in `linux_main.cpp`, values from `src/platform/story_hud.cpp`) and calls `ui::set_hud`; the presentation thread rebuilds the HUD's markup only when it changes. The HUD is hidden while a menu is open and outside Story play. It takes no input. A media query (`orientation: portrait`) turns the two columns into rows above and below the game's picture.

Hiding the original HUD: hooks mark the game's single-player HUD routine (`func_80075CD8`), and while BlockPlanet's HUD is shown the draw filter skips the 2D helpers called inside it; the 3D piece queue (`func_800A3E6C`) is skipped too. Checked at 16:9, 4:3, 21:9 and portrait (600 × 840).

**Case (decided 2026-11-07):** no all-capitals text. BlockPlanet's own screens use Title Case for labels and sentence case for sentences, and the game's own capitals are converted the same way (`tetrisphere::proper_case`). The title's notice and the pause screen's heading follow it too. The one exception: a warning may use capitals for emphasis (sparingly). The name keyboard's SHIFT label shows capitals on.
